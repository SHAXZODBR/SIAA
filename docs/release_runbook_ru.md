# Регламент релиза — дообучение модели триажа мозга на новой партии данных клиники

Экземпляр для основателя / ML-инженера. Английская версия: `release_runbook_en.md`. Контракт, по
которому написан каждый этап: `dev/release_pipeline_contract.md`. Оркестратор:
`scripts/release_pipeline.py`.

Цель: новая партия МРТ / КТ головного мозга **с заключениями рентгенологов** приезжает на диске →
одна возобновляемая команда оценивает модель, поставляемую сегодня, на новых пациентах, обучает
кандидата (только на МРТ-исследованиях), проверяет его на зафиксированных отложенных
пациентах, продвигает в релиз, переписывает все закреплённые числа в коде и документации и
публикует бандл модели → вы ставите тег приложения, CI собирает установщик, клиника его получает.
Ничего из `data/` и `models/` никогда не коммитится; имена пациентов не попадают ни в один
выходной файл.

## 1. Что покрывает этот регламент

| | |
|---|---|
| Вход | корень диска с одной папкой на исследование (DICOM) + заключения к этим исследованиям (одна или несколько поставок) |
| Выход | `models/brain_triage_finetuned/` (новая идентичность), обновлённые документы/код, бандл в `data/release/<tag>/`, GitHub-релиз модели, затем установщик, собранный CI |
| Кто | один человек на обучающем Mac (Apple Silicon, MPS); ~1 рабочий день реального времени на 5 000 исследований, в основном без присмотра |
| Никогда | `git push`, `git tag` и секрет GitHub скрипт **не трогает** — это ваши ручные шаги в разделе 8 |

5. **Текущий релиз цел**: существуют `models/brain_triage_finetuned/{model.safetensors,MANIFEST.json,study_level_eval.json}` и `data/holdout_patients_v1.txt` (178 зафиксированных id пациентов).

### 2a. Когда пришёл диск — приём (intake) и зеркало

Никогда не обучайте прямо с диска клиники: сначала заархивируйте его (с контрольными суммами и
записью в реестр), затем отзеркальте архив на второй диск, и только потом запускайте релиз с архивной копии.

1. **Подключите** диск клиники и архивный диск (`SIAA_DATA`, зашифрованный). Оба скрипта отказываются
   работать с несуществующим назначением, поэтому неподключённый `/Volumes/…` никогда не заполнится на внутреннем диске.
2. **Приём** — копирование в `<SIAA_DATA>/raw/<clinic>/<batch>/{images,reports}`:

   ```sh
   /Users/shakhzodbtr/venv/bin/python scripts/intake_batch.py --src /Volumes/HOSPITAL/new2 \
       --reports /Volumes/HOSPITAL/reports_new2 --clinic shox --batch new2 --dest /Volumes/SIAA_DATA
   ```
   - Источник только читается. Каждый файл копируется с вычислением sha256 на лету, переименовывается
     на место, записывается в журнал, затем **перечитывается с архивного диска и проверяется**.
     `CHECKSUMS.sha256` (и `CHECKSUMS.sizes`) перечисляют все файлы в формате `shasum`:
     `cd <папка партии> && shasum -a 256 -c CHECKSUMS.sha256`.
   - `README.txt` фиксирует дату получения (`--received YYYY-MM-DD`, по умолчанию сегодня), источники,
     число файлов и — по быстрому чтению заголовков скопированных снимков (`index_new_studies.py --limit 200`) —
     модальности и диапазон дат исследований (с пометкой «sample», если исследований в партии больше).
     В `raw/INVENTORY.csv` пишется одна строка на партию — только после полностью проверенного приёма.
   - Прервалось или заключения придут позже → та же команда с `--resume` (скопированные файлы
     пропускаются, недокопированный `.part` переделывается; `--resume --reports <папка>` добавляет только
     заключения). Существующая папка партии без `--resume` никогда не перезаписывается.
   - Код 3 = копия отличается от источника (список в `.intake/needs_recopy.txt`; следующий `--resume`
     копирует их заново — проверьте архивный диск). Код 2 = нечитаемые файлы источника (битые сектора?);
     всё остальное скопировано. `--verify` в любой момент заново хеширует всю архивную партию.
   - Скрипт печатает точные команды `release_pipeline.py plan` / `run` для партии
     (`--root` = папка с папками исследований, `--reports` = архивные заключения).
   - **Одна папка (или один файл) заключений за запуск.** Её файлы копируются в `reports/` под своими
     именами. Следующая поставка заключений к тем же снимкам оформляется отдельной партией, только с заключениями:

     ```sh
     /Users/shakhzodbtr/venv/bin/python scripts/intake_batch.py --reports /Volumes/HOSPITAL/reports_new2_B \
         --clinic shox --batch new2_reports_B --dest /Volumes/SIAA_DATA
     ```
     Не добавляйте её в первую партию через `--resume --reports`: файл, чьё имя уже есть в архиве,
     отклоняется, если размер другой («a batch is one delivery»), и **пропускается как уже скопированный**,
     если размер тот же, а новые имена смешались бы в одной папке `reports/`, где этап parse уже не
     различит поставки. Напечатанная скриптом команда называет только его собственную папку `reports/`;
     для релиза передайте в `--reports` все архивные папки заключений, от старой поставки к новой (раздел 4b).
3. **Зеркало** архива на резервный диск (сначала пробный прогон, затем подтверждение):

   ```sh
   scripts/backup_mirror.sh /Volumes/SIAA_DATA /Volumes/SIAA_BACKUP            # спросит «Type yes»
   scripts/backup_mirror.sh --yes /Volumes/SIAA_DATA /Volumes/SIAA_BACKUP      # без вопросов
   ```
   `rsync -a --checksum --delete-after` после пробного прогона, который печатает, сколько файлов будет
   скопировано и **удалено** на резервном диске; затем 50 случайных файлов хешируются с обеих сторон
   (`--sample N`). Скрипт отказывается, если `raw/INVENTORY.csv` резервного диска новее архивного (диски
   перепутаны или партия заархивирована только на резервном — зеркало её удалит) и если архив пуст.
   Код 0 — ок · 1 — отказ / нет подтверждения · 2 — ошибка rsync · 3 — выборочная проверка не прошла.
   `--verify-only` перепроверяет выборку без копирования (раз в месяц).
4. Отключайте и возвращайте диск клиники только после того, как шаг 3 напечатал `B is a verified mirror of A`.

## 3. Оценки времени (5 000 исследований, Apple Silicon)

| Этап | Ожидаемое время | Примечания |
|---|---|---|
| index | 10–30 мин | один DICOM-заголовок на серию; возобновляемый |
| parse | минуты | ~5 000 PDF; xlsx/csv — секунды; несколько поставок разбираются за один запуск |
| label + benchmark | < 1 мин | только правила; LLM-проход (`--label-llm`) необязателен и медленнее; второе прочтение (раздел 7) — отдельный ручной шаг |
| match | секунды | нужен индекс, не диск |
| build | ~1 исследование / с → ~1,5 ч | возобновляемый, переиспользует готовые PNG, подтверждённые как МРТ; первая сборка по правилу «только МРТ» набора, собранного старой версией, заново читает все исследования |
| prospective | минуты (на полной партии ещё не замерялось) | один проход модели по срезам партии, как в gate; диск не нужен |
| combine | минуты | симлинки + манифест |
| train | ≈ 45 мин на 3 500 срезов → **≈ 5 ч** на 5 000 исследований (12 эпох) | MPS; Mac на питании, крышка открыта |
| gate | ~5 мин | кандидат + старая модель на одном и том же val |
| promote, bump | секунды | |
| bundle | 5–15 мин | zip, разбиение, загрузка, проверка восстановления |

## 4. Путь в одну команду

```sh
cd ~/Desktop/Siaa_ai/sentinel
/Users/shakhzodbtr/venv/bin/python scripts/release_pipeline.py plan --batch new1 \
    --root /Volumes/Transcend/new1 --reports ~/Desktop/reports_new1          # сначала прочитайте
/Users/shakhzodbtr/venv/bin/python scripts/release_pipeline.py run  --batch new1 \
    --root /Volumes/Transcend/new1 --reports ~/Desktop/reports_new1
```

- `plan` печатает shell, который можно скопировать и вставить (каждая команда, защитные проверки
  комментариями), и ничего не запускает. В заголовке он называет источники заключений в том порядке,
  в каком их прочтёт parse (`# report sources (oldest delivery first): …`), и правило сборки
  (`# modality rule (build): …`).
- `run` выполняет двенадцать этапов по порядку (index → parse → label → match → build → prospective →
  combine → train → gate → promote → bump → bundle), пишет лог каждого в
  `data/release/<tag>/logs/<stage>.log`, вывод защитных проверок — в `data/release/<tag>/logs/guards.log`,
  и ведёт `data/release/<tag>/state.json` (все действующие параметры, статус / входы / выходы каждого
  этапа, вердикты проверок).
- **Тег фиксирован на весь релиз.** Первая напечатанная строка — `tag: <tag> (…)`. Первый `run`
  выбирает следующий свободный `brain-triage-v<N>` и записывает его в `data/release/LATEST`; каждый
  следующий запуск без `--tag` продолжает LATEST (`tag: <tag> (from LATEST)`), пока его этап `bundle` не
  выполнен — даже после того как `promote` создал новую папку `models/brain_triage_finetuned_prev_*`.
  `--tag` нужен только чтобы задать имя самому или вернуться к старому релизу.
- При первом сбое останавливается, печатает упавшую команду, путь к логу и точную строку
  `… run … --resume`, в которой повторены **все** параметры запуска (`--epochs`, `--device`,
  `--python`, `--base-model`, `--llm-labels`, …). Устраните причину и вставьте эту строку. Короткая
  форма `/Users/shakhzodbtr/venv/bin/python scripts/release_pipeline.py run --batch new1 --resume`
  делает то же самое: тег из LATEST, параметры из `state.json` (печатаются как `options from state.json: …`).
- `--dry-run` печатает команды, ничего не запуская; `--from <stage>` / `--only <stage>` (или просто
  `release_pipeline.py <stage> …`) сужают запуск; `status` показывает таблицу состояния.
- Старые наборы объединяются автоматически: `data/local_finetune_bin` (партия 1) плюс все
  `data/sets/*`, кроме текущей партии и репетиционных наборов (`data/sets/rehearsal_*`), от старых к
  новым; текущая партия идёт **последней**, потому что `combine` даёт каждому пациенту ОДИН класс, и
  при конфликте меток побеждает последний набор в командной строке (конфликты печатаются и
  записываются в `dataset_manifest.json`). Переопределяется через `--extra-sets`.
- Пациенты, на которых обучена текущая модель, остаются в `train`: `train/` старого набора всегда, а
  начиная со второго переобученного релиза набор, указанный в `training_metrics.json` текущей модели,
  автоматически передаётся как `--train-lock data/train_release_<предыдущий тег>` (`plan` его
  печатает), а этапу `prospective` — как дополнительный `--seen` (раздел 4d).
  `--train-lock <ids.txt | папка релизного набора>` задаёт его вручную.

### 4a. Два кандидата: `--candidates warm,fresh`

По умолчанию (`--candidates warm`) один кандидат дообучается от текущего релиза (`--base-model`,
по умолчанию `models/brain_triage_finetuned`) — ровно команды выше. С `--candidates warm,fresh`
конвейер дополнительно обучает **fresh**-кандидата от публичного ImageNet ViT
(`models/hf/google__vit-base-patch16-224`, если есть офлайн-копия, иначе `google/vit-base-patch16-224`
из кэша Hugging Face, с `--base-model-fresh`) и оставляет лучшего:

```sh
/Users/shakhzodbtr/venv/bin/python scripts/release_pipeline.py run --batch new2 \
    --root /Volumes/SIAA_DATA/raw/shox/new2/images --reports /Volumes/SIAA_DATA/raw/shox/new2/reports \
    --candidates warm,fresh
```

- `train` пишет `models/brain_triage_candidate_<tag>_warm` и `…_fresh` (≈ 2 × время обучения и места на
  диске); `gate` оценивает **каждого** с `--compare-with models/brain_triage_finetuned` на одном и том же val.
- `promote` переносит лучшего кандидата, который **прошёл гейт с `promotion.promote = true`**, по
  сбалансированной точности; при равенстве выигрывает `warm`. Кандидат ниже порога (код 2) или не лучше
  текущего релиза (код 4) не продвигается никогда, какими бы ни были остальные числа. Если не подходит
  ни один, запуск останавливается до `promote` с тем же сообщением `GATE FAILED` / `NOT PROMOTED`, что в разделе 7.
- Проверка перед обучением убеждается, что fresh-база лежит на этом Mac (**во время релиза ничего не
  скачивается**; этапы работают с `HF_HUB_OFFLINE=1`): `fresh base not available offline` останавливает
  запуск до любого обучения и печатает команду загрузки для машины с интернетом — скопируйте полученную
  `models/hf/google__vit-base-patch16-224/` в репозиторий.
- `state.json` → `candidates.<warm|fresh>` (путь, база, коды выхода train / gate, sens / spec / balanced,
  вердикт) и `candidate_choice` (выбранный кандидат и рейтинг с причиной отказа каждому); их показывают
  `plan`, `status` и печатаемая строка возобновления. `--resume` после того, как один кандидат
  доучился, переобучает только другого.
- Непродвинутый кандидат остаётся в `models/`; удалите его после публикации релиза.

### 4b. Несколько поставок заключений: `--reports A B …`

Если заключения одной партии пришли несколькими поставками, передайте каждую в `--reports`,
**от старой к новой** (один флаг с несколькими путями или повторённый флаг — оба дописывают):

```sh
/Users/shakhzodbtr/venv/bin/python scripts/release_pipeline.py run --batch new1 \
    --root /Volumes/Transcend/new1 --reports ~/Desktop/reports_new1_A ~/Desktop/reports_new1_B
```

- Этап parse передаёт их в `parse_hospital_reports.py --src A B` в этом порядке и пишет одну таблицу.
  Каждый файл разбирается как раньше; затем строки сверяются **между файлами**: секция, повторяющая
  уже взятую из более раннего файла (тот же пациент, дата, модальность, область, заголовок секции и
  заключение), отбрасывается как повтор, а новая секция, чей ключ (patient_id, study_date, modality,
  section_index) уже занят более ранним файлом, получает следующий свободный `section_index`.
- Повторы отбрасываются **по счёту, а не по простому наличию**: если более ранние файлы взяли секцию
  один раз, более поздний файл теряет не больше одной её копии, так что вторая, такая же на вид секция
  того же визита сохраняется. Секция с другим заголовком (например МРТ головного мозга и МР-ангиография
  в один день с одинаковым заключением) повтором не считается никогда. Секция без даты никогда не
  отбрасывается как повтор (но перенумеровывается, если её ключ занят). У строки листа запроса и
  секции PDF одного и того же исследования разные заголовки, поэтому сохраняются обе: не передавайте
  лист и PDF одних и тех же исследований как две поставки.
- Почему от старой к новой: метки (по правилам, импортированные LLM-метки) привязываются по этому
  ключу, поэтому он должен указывать ровно на одну секцию и не меняться. Строки более ранней поставки
  никогда не меняются, так что добавление поставки B не сдвигает ни одну метку, поставленную на поставке A.
- При нескольких источниках (или если что-то было сверено) сводка parse печатает число файлов по
  источникам (`Sources (oldest first): files per source <A> + <B>`) и
  `N rows dropped as repeats across files · M rows renumbered (section_index taken by an earlier file)`.
  Только счётчики — никогда имя файла или текст заключения.
- Если хотя бы один источник отсутствует или не содержит файлов заключений, parse останавливается
  (код 1) и называет его (`source 2 of 2`); CSV не пишется.
- Порядок входит в отпечаток parse: добавленный источник или переставленный порядок заново запускает
  `parse` при `--resume`, а с ним каждый следующий этап, чьи входы изменились. Релиз, прошедший с одним
  источником, сохраняет `parse` и `label` выполненными, пока этот источник не изменился.

### 4c. Только МРТ: `--modality`

Валидированная модель триажа — МРТ-модель, но сопоставленное исследование «мозга» может оказаться КТ
головы. Поэтому этап `build` по умолчанию идёт с `--modality MR` (правило «только МРТ»); `--modality any`
отключает правило. Значение хранится в `state.json`; его смена заново запускает `build` и следующие
этапы (но не `match`). Этап `build`, записанный старой версией скрипта, до появления правила, считается
выполненным с `--modality any`: `--resume` до `promote` заново запускает его по правилу (и этапы после него).

- **Уровень строк**, до чтения DICOM: сопоставленная строка, чей столбец `modality` называет другую
  модальность получения изображений (`CT`), отбрасывается. Строка с пустым или не-image значением (`SR`,
  `PR`, `OT` — старые индексы пишут `SR` у многих МРТ-исследований) остаётся и решается при сборке.
- **Время сборки** (истина): DICOM Modality той самой серии, из которой берутся срезы, должна быть `MR`.
  Иначе исследование не получает срезов; его строка в `studies.csv` остаётся с `n_slices` 0, и оно
  считается исключённым, а не упавшим.
- **Сводка**: `modality rule: --modality MR`, затем `rows dropped before reading DICOM: modality CT=…`
  и `studies excluded at build time (kept in studies.csv, n_slices 0): modality CT (series)=…,
  modality unknown (series)=…`. Если после правила не осталось ни одного исследования со срезами,
  `build` завершается с кодом 1 (`no study produced slices: …`), и релиз останавливается.
- **`studies.csv`** получил новый последний столбец `modality`: Modality серии, из которой взяты срезы
  (у исключённого исследования — найденная модальность; пусто, если не проверено). Готовые PNG
  переиспользуются, только если предыдущий `studies.csv` записал для исследования `MR`, поэтому набор,
  собранный старой версией, один раз читается заново (так же долго, как первая сборка); исследование,
  уже признанное КТ, повторно не читается.
- Правило действует на набор, который собирает этот релиз (`data/sets/<batch>`). Старый набор партии 1
  `data/local_finetune_bin` — как и любой другой набор, уже лежащий в `data/sets/`, — объединяется
  **как есть**: он не пересобирается и не перепроверяется.

### 4d. Проспективная проверка: поставляемая модель на пациентах, которых она не видела

Этап `prospective` отвечает на один вопрос: **как модель, которая сегодня работает в клинике, справляется
с пациентами, которых она никогда не видела?** Он идёт после `build` и **до** того, как партию используют
`combine` / `train`.

- Он оценивает каждое исследование `data/sets/<batch>` (по правилу — только МРТ; строки `needs_review`
  `build` уже исключил) релизом, поставляемым сегодня, `models/brain_triage_finetuned` — всегда этой
  папкой, с какого бы `--base-model` ни стартовало обучение; её файлы сначала сверяются с её
  `MANIFEST.json` — по продакшн-протоколу (предиктор реестра, среднее по центральным срезам,
  порог 0,50). Будущего релиза ещё нет; ничего заранее не переобучается.
- В `--seen` передаются наборы, которые получает `combine` (включая `data/local_finetune_bin`),
  **плюс релизный набор, на котором обучена поставляемая модель** (`data/train_release_<предыдущий тег>`,
  указанный в её `training_metrics.json`, или `--train-lock`, если это папка) — начиная со второго
  переобученного релиза; `plan` его печатает. Модель, обученная только на старом наборе, ничего не добавляет.
- Если этого релизного набора нет или он пересобран, проверка перед `prospective` останавливает запуск
  до какой-либо оценки (`guard rails before prospective failed`): без него группа `new` включала бы
  пациентов, на которых модель обучалась. Восстановите папку или передайте `--train-lock <папка
  релизного набора>` с набором, на котором она обучена (файла со списком id здесь недостаточно: `--seen`
  принимает только папки).
- Пациенты делятся на группы: `new` (нет ни в одном наборе `--seen`), `holdout` (178 зафиксированных
  пациентов или `val/` релизного набора или старого набора), `seen_train` (`train/` или `tune/` этих
  наборов, а также **каждый** пациент более раннего набора партии `data/sets/<batch>`, которого нет в
  источниках holdout: деление такого набора на train/val лишь рекомендательное, `combine` делит его
  заново, поэтому его пациенты считаются увиденными — никогда не `new`), `all` и `new_same_date`
  (исследования группы `new`, у которых заключение и снимки одного дня: самая чистая эталонная метка). Пациент из более раннего набора
  считается увиденным, даже если поставляемая модель на этом наборе не обучалась, — группа `new`
  ошибается в безопасную сторону.
- Результат: `data/release/<tag>/prospective_eval.json` (`kind: prospective_eval`), полная таблица в
  `logs/prospective.log` и одна строка после этапа:
  `prospective, never-seen patients: n N studies · sensitivity x · specificity y`.
- **Читайте главную группу `new`** (`groups.new` в JSON): `n_studies` / `n_patients`, `tp fn tn fp`,
  `sensitivity` с `sensitivity_ci95`, `specificity` с `specificity_ci95`, `balanced_accuracy`, `ppv`,
  `npv`, `flag_rate`, `prevalence`, `auc`. Сначала смотрите на ширину интервалов, потом на сами значения.
  `threshold_sweep_new` — только описательный (порог поставки остаётся 0,50), `findings_new` показывает
  обнаружение по находкам, `notes` перечисляет, что нужно учесть.
- **Он никогда не блокирует релиз.** Код 0 означает, что оценка прошла, какими бы ни были числа. Код 2
  означает непригодный вход (модель не загружается, в наборе нет PNG …): обычный сбой этапа — устраните
  причину и возобновите.
- **После `promote` он под тем же тегом больше не запускается** (к этому моменту в
  `models/brain_triage_finetuned` лежит новая модель, обученная на этих пациентах). Сохраните JSON: это
  единственное измерение старой модели на них. У релиза, продвинутого старой версией скрипта, когда
  этого этапа ещё не было, записи `prospective` нет: `run … --resume` его завершает (`bump`, `bundle`),
  а `run` / `status` показывают `prospective skipped (promoted before this stage existed)`.
- **Именно эти числа, а не числа гейта, описывают реальную работу на новых пациентах.** Набор гейта
  используется из релиза в релиз, и кандидата выбирают по нему; модель в проспективной проверке
  заморожена до появления этих заключений. Честные ограничения: эталонные метки взяты из рутинного
  заключения (разобранного, один рентгенолог, при желании — второе LLM-прочтение), а не из
  согласованного чтения; это одна клиника и та партия, которую она прислала, а не заранее
  зарегистрированная последовательная когорта; пограничных заключений (`needs_review`) и КТ в ней нет.
  Работу нового релиза на новых пациентах измерит этап `prospective` следующей партии.

train/val/tune нет и каждый holdout-id в `val`, есть `tune/` (тренер запускается с `--select-split tune`;

локальный релизный набор). **Перед `prospective`**: релизный набор, на котором обучена поставляемая
модель (если он есть), на месте и не изменён, поэтому передаётся как `--seen`, — или `--train-lock`
называет его папкой (раздел 4d). **Перед `combine`**: тот же набор на месте и не изменён (его пациенты
закреплены за `train`), или задан `--train-lock`. **Перед `bundle`**: гейт
пройден и promotion = true у продвинутой модели, плюс все правила `promote_model.py` (релизные пороги,
продакшн-протокол, релизный val / покрытие holdout, оценка привязана к этим весам),
`bump_model_release.py --check` чист, полный `pytest -q` и `docs/test_docs_consistency.py` зелёные
(это единственное место, где запускается весь набор тестов). Полный вывод проверок пишется в
`data/release/<tag>/logs/guards.log`, вердикт — в `state.json` (`guards.pre_train`, `guards.pre_bundle`).

## 6. Правила go / no-go

| Правило | Порог | Где проверяется |
|---|---|---|
| Порог чувствительности на уровне исследования | ≥ 0,85 | `eval_study_level.py --min-sens` (код 2) |
| Порог специфичности на уровне исследования | ≥ 0,40 | `eval_study_level.py --min-spec` (код 2) |
| Продвижение относительно текущего релиза | новая проходит гейт **и** balanced accuracy ≥ старая − 0,01 **и** чувствительность ≥ старая − 0,03 | `eval_study_level.py --compare-with` (код 4), `promote_model.py` |
| Зафиксированные отложенные пациенты | все 178 id из `data/holdout_patients_v1.txt` в `val`; ни одного в `train` | `combine_training_sets.py`, проверка оркестратора перед train |
| Минимум нормы в партии | предупреждение ниже 300 сопоставленных нормальных исследований — без них специфичность не сдвинется | проверка оркестратора перед train |
| Качество разметки | правила согласуются с эталоном на 894 пациента по `abnormal` ≥ 0,90 | `label_reports.py --benchmark` |
| Манифест | sha256 весов закреплён в `MANIFEST.json`, проверяется перед каждой оценкой | `eval_study_level.py` (код 3) |
| Релизный протокол | оценка выполнена с релизными порогами, продакшн-гейтом (`gate mean @0.50`, предобработка предиктора реестра), на релизном val (его sha256 пациентов = `dataset_manifest.json` → `splits.val.patients_sha256`; для старой папки val оценены все holdout-id — `eval_study_level.py --holdout`, по умолчанию `data/holdout_patients_v1.txt`, `none` — пропустить) и для этих весов | `promote_model.py` (отказ, код 1), проверка перед bundle, `publish_model_bundle.py` |

`promote_model.py --force` отменяет **только** `promotion.promote = false` (сравнение старой и новой
модели; записывается как `forced` в `promotion_log.json`, и `publish_model_bundle.py` затем отказывает
такой модели без `--allow-unvalidated`). Он никогда не отменяет проваленный гейт, пониженные пороги,
не продакшн-гейт или предобработку, неверный val / непокрытый holdout или оценку других весов — такие
отказы печатают `not overridable` и `[--force ignored]`. Для старой папки val `promote_model.py
--holdout` задаёт файл закреплённого holdout (по умолчанию `data/holdout_patients_v1.txt`).

Падение чувствительности никогда не обменивается на рост специфичности: если кандидат
специфичнее, но пропускает больше патологии, чем допускает правило, он **не** продвигается.

## 7. Что делать, если гейт не пройден

Этап `gate` останавливает запуск **до `promote`** двумя разными способами; в обоих случаях
`models/brain_triage_finetuned` не тронута, а `state.json` хранит вердикт (его показывает `status`):

| Код | Печатает | Значение |
|---|---|---|
| 2 | `GATE FAILED` (вердикт `gate_failed`) | кандидат ниже порога (sens ≥ 0,85 / spec ≥ 0,40) |
| 4 | `NOT PROMOTED` (вердикт `not_promoted`) | кандидат проходит пороги, но не лучше текущего релиза (правило продвижения, раздел 6) |

1. Прочитайте `models/brain_triage_candidate_<tag>/study_level_eval.json` и `data/release/<tag>/logs/gate.log`: какой порог не взят, насколько широк ДИ, `promotion.reason`.
2. **Оставьте старую модель** — это всегда допустимый исход. Ничего не продвинуто; у клиники остаётся текущий релиз. Папку кандидата удалите или сохраните; `data/release/<tag>/` фиксирует, что было испробовано.
3. **Слишком низкая специфичность** (обычный случай): в партии мало нормы. Запросите у клиники больше *нормальных* исследований мозга с заключениями (лист запроса из раздела 2), соберите новую партию, обучите снова. Порог не снижайте.
4. **Слишком низкая чувствительность**: сначала проверьте разметку — выполните двухраундовое второе LLM-прочтение меток (команды ниже), затем посмотрите `results` в JSON оценки для агрегации `mean` при других порогах — смена порога это изменение **продукта** (`brain_analysis.py`), а не ручка, чтобы пройти гейт.
5. **Переобучение с публичной базы ViT** (запасной путь, если дообучение текущего релиза снова и снова не проходит): этап train стартует с `--base-model` (по умолчанию `models/brain_triage_finetuned`). Используйте офлайн-копию `models/hf/google__vit-base-patch16-224`, если она есть, иначе id `google/vit-base-patch16-224` (уже лежит в `~/.cache/huggingface` на этом Mac; сообщение о провале гейта печатает нужный вариант). Гейт по-прежнему сравнивает с текущим релизом. Вставьте строку, которую напечатал провал гейта, или:

   ```sh
   /Users/shakhzodbtr/venv/bin/python scripts/release_pipeline.py run --batch new1 --tag <tag> \
       --base-model google/vit-base-patch16-224 --from train
   ```

## 9. Возобновление, статус и устранение неполадок

- `/Users/shakhzodbtr/venv/bin/python scripts/release_pipeline.py status --batch <batch>` — таблица этапов (pending / running / done / archived / failed) с путями к логам, вердиктами проверок и вердиктом гейта; тег берётся из `data/release/LATEST`.
- `--resume` пропускает этап со статусом `done`, чьи выходы на месте и входы не изменились (sha256 входных файлов: `studies.csv` каждого объединяемого набора — для старого набора без него отсортированный список файлов, — файлы holdout и train-lock, `dataset_manifest.json`, веса кандидата, JSONL с LLM-метками; скрытые файлы вроде `.DS_Store` из Finder не учитываются; для `parse` также порядок источников заключений, если их несколько, для `build` значение `--modality`, для `prospective` `MANIFEST.json` поставляемой модели, для `train` значения `--base-model` и `--epochs`); иначе этап выполняется заново.
- `promote` **перемещает** папку кандидата в `models/brain_triage_finetuned`. Он записывает `archived_candidate` в `state.json` и помечает `train` и `gate` как `archived` (= выполнено), поэтому возобновление после promote выполняет только оставшееся (`bump`, `bundle`). Этап, чьих выходов уже нет, тоже считается выполненным, если выполнен более поздний этап, — если только его не называет `--from` / `--only`. После promote этапы `prospective` / `combine` / `train` / `gate` / `promote` под тем же тегом больше не запускаются (гейт сравнил бы нового кандидата с самим собой; combine переписал бы val-набор, к которому привязана оценка продвинутой модели; prospective оценил бы новую модель на её же обучающих пациентах), а `--resume` считает все этапы до `promote` замороженными, даже если какой-то входной файл с тех пор изменился, — остаются только `bump` и `bundle`. Изменения после promote идут в следующий релиз (новый тег).
- Релиз, продвинутый старой версией скрипта (когда этапа `prospective` ещё не было), завершается так же: `run --batch <batch> --resume` выполняет `bump` и `bundle`; `prospective` в `run` и `status` показан как `skipped (promoted before this stage existed)` и под этим тегом никогда не запускается.
- Этап `build`, записанный старой версией до правила «только МРТ», считается выполненным с `--modality any`: `--resume` до promote заново запускает `build` по правилу (`stage build re-run: inputs changed`), а с ним и все последующие этапы.
- Train-lock: `combine` закрепляет в `train` пациентов, на которых обучена текущая модель релиза (`data/train_release_<предыдущий тег>`, из её `training_metrics.json`), а `prospective` передаёт тот же набор как `--seen`. Сохраняйте эту папку. Если её нет или она пересобрана, проверка перед `prospective` (и перед `combine`) останавливает запуск; восстановите папку или передайте `--train-lock <папка релизного набора>` с набором, на котором обучена эта модель. `--train-lock <ids.txt>` со списком id пациентов удовлетворяет только `combine` — `prospective` всё равно отказывает, потому что его `--seen` принимает только папки.
- Выбор контрольной точки: `combine` пишет сплит `tune/` (часть новых пациентов train); тренер запускается с `--select-split tune` и выбирает лучшую эпоху по `tune/`, никогда по `val` (набору гейта). Проверка перед train останавливает релиз, если `tune/` нет (перезапустите `combine` с `--tune-frac > 0`).
- `bundle` отказывает (код 1) → либо модель не валидирована (`publish_model_bundle.py` проверяет те же факты гейта; `--allow-unvalidated` — только для демо, пишет `validated: false` в `manifest.json`), либо GitHub-релиз с этим тегом уже содержит бандл **другой** идентичности модели (`--replace-existing` перезаписывает его намеренно). Повторный запуск с тем же бандлом переиспользует загруженные ассеты, поэтому id ассета манифеста не меняется; `--reupload` загружает заново (новый id ассета; CI это не затрагивает — он ищет релиз по тегу). Без `--tag` `publish_model_bundle.py` использует тег `brain-triage-<identity12>`; оркестратор использует этот тег по умолчанию, и именно его ищет CI установщиков.
- Диск не смонтирован → он нужен только `index` и `build` (`match` читает индекс, `prospective` — собранный набор). `--resume` без диска выполняет то, что может (`parse`, `label`, `match`), и аккуратно останавливается перед `build` с `drive not mounted: <root> (needed by stage build)`. Смонтируйте и вставьте напечатанную строку возобновления. Когда `build` выполнен, остаток релиза (`prospective` → `bundle`, включая `train`) идёт без диска.
- Индекс, записанный до исправления заголовков изображений: исследование, у которого первым шёл структурированный отчёт (или presentation state), проиндексировано с модальностью `SR` и пустой областью, и `match` может не признать его исследованием мозга. `index` возобновляемый и исправляет это сам: строка с модальностью `SR` / `PR` / пустой (и без ошибки) индексируется заново при следующем запуске (`re-indexing N studies whose row was described by a non-image object`). В исследовании, выгруженном «плоско» (объект-отчёт и снимки в одной папке, отчёт первым), индексатор читает следующие заголовки этой папки, до 50, пока не найдёт изображение. Исследование совсем без объекта-изображения записывается с ошибкой `no image object` (`no image object in the first 50 headers of each folder`, если упёрлось в предел) и больше не индексируется заново при каждом возобновлении; `match` исключает строки с ошибкой, поэтому его заключение считается несопоставленным.
