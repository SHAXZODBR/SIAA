# SIAA — Sentinel Medical AI · Выдача лицензии и модели клинике (сторона поставщика)

Версия 1.1.0 · Редакция документа 2026-11 · **Внутренний документ — только для сотрудников поставщика, никогда не передавайте его клинике**

Это процедура на стороне поставщика: отпечаток ПК клиники превращается в подписанную лицензию и копию валидированной модели триажа, которую может расшифровать только этот ПК. Половина процедуры на стороне клиники описана в § 5.3–§ 5.4 руководства администратора (`admin_install_guide_ru.md`); английская версия этого документа — `vendor_provisioning_en.md`.

---

## 1. Общая схема

```
ПК клиники                         Mac поставщика                                ПК клиники
отпечаток (64 hex)    ──────────►  packaging/provision_clinic.py  ──── USB ────►  1. импорт license.dat, перезапуск
(Настройки → Лицензия)             • license.dat (с model_key_secret)             2. Импорт пакета модели (POST /models/import)
                                   • brain_triage_finetuned_<id12>_<fp8>.zip      3. проверка идентификатора: уведомление, /health, PDF
                                   • README_admin_ru.txt / README_admin_en.txt
                                   • строка в data/licenses/ledger.csv
```

- Клиника получает **клинический вариант установщика** (`sentinel-windows-x64-NO-VALIDATED-MODEL`): в нём нет весов собственной модели поставщика, его можно свободно копировать.
- Валидированная модель попадает в клинику только как пакет, зашифрованный ключом `HKDF(model_key_secret ‖ отпечаток машины)`. `model_key_secret` передаётся **внутри подписанной лицензии**, поэтому поставщик шифрует без связи с клиникой, а клиника никогда не видит открытых весов; на любом другом ПК и без этой лицензии пакет бесполезен.
- Поэтому лицензия и пакет — **пара**: каждый запуск выдачи создаёт оба файла, и оба импортируются вместе.

## 2. Что нужно на Mac поставщика

| Что | Где | Проверка |
|---|---|---|
| Ключ подписи поставщика | `vendor_keys/vendor_private_key.pem` (никогда в git, никогда на ПК клиники; резервная копия — офлайн) | `ls -l vendor_keys/` — файл есть и доступен только вам |
| Валидированный выпуск модели | `models/brain_triage_finetuned/` с `MANIFEST.json`, `study_level_eval.json`, `promotion_log.json` | выпускной барьер пройден, продвижение **не** было принудительным (иначе утилита откажет, § 4) |
| Среда Python | venv репозитория (`/Users/shakhzodbtr/venv/bin/python` на сборочном Mac) | `python -m src.utils.model_crypto keyinfo` выполняется |
| Клинический установщик | GitHub Actions → **Build installers** → **Run workflow** со **снятой** отметкой `include_validated_model` → артефакт `sentinel-windows-x64-NO-VALIDATED-MODEL` | скачайте сразу: артефакты удаляются через 1 день |
| Папка реестра | `data/licenses/` (игнорируется git) | создаётся утилитой при первом запуске |

## 3. Шаг 1 — получить отпечаток от клиники

1. ИТ-специалист клиники устанавливает клинический вариант и открывает *Настройки → Лицензия* (или шаг *Лицензия* мастера первичной настройки). На экране — **отпечаток машины**: 64 шестнадцатеричных символа.
2. Клиника присылает эту строку и юридическое название клиники. Фотографии экрана недостаточно — просите текст (один неверный символ даёт лицензию для другой машины).
3. Проверьте: ровно 64 символа `0-9a-f`. Первые 8 символов (`fp8`) входят в имя каждого файла этой поставки.

Отпечаток вычисляется из имени хоста, ОС, модели ЦП, основного MAC-адреса и идентификатора машины ОС. Попросите клинику **до** отправки отпечатка закончить переименование ПК, ввод в домен и установку сетевых карт.

## 4. Шаг 2 — выдача на Mac поставщика

```
python packaging/provision_clinic.py --fingerprint <отпечаток, 64 hex> --customer "<юр. название клиники>" \
       --expires 2027-12-31 [--tier pro] [--features ...] \
       [--model models/brain_triage_finetuned] \
       [--private-key vendor_keys/vendor_private_key.pem] --out <папка поставки>
```

Что делает утилита:

1. **Отказывает** (код выхода 1, печатается код причины, ничего не записывается) при `bad_fingerprint` (не 64 шестнадцатеричных символа), `bad_customer` (пустой `--customer`), `bad_expiry` (не `ГГГГ-ММ-ДД` или дата не в будущем), `model_missing`, `manifest_missing`, `release_check` (`study_level_eval.json` модели не проходит правила выпуска — те же причины, что в `scripts/promote_model.py` и в проверке пакета для установщика), `forced_promotion` (`promotion_log.json` фиксирует принудительное продвижение), `private_key` (ключ не читается или это не тот ключ, которому доверяет приложение), `output_exists` (папка поставки никогда не перезаписывается) и `output_in_repo` (`--out` указывает на папку внутри репозитория: там поставка не игнорируется git, а репозиторий публичный — используйте папку вне его, например `~/sentinel_deliveries/`). Клиника никогда не получает модель, не прошедшую барьер.
2. Выпускает `license.dat` со свежим случайным `model_key_secret` внутри подписанных данных — эквивалент `python -m src.utils.license issue … --with-model-key`. Ничего секретного не печатается.
3. Копирует модель во **временную** папку и шифрует копию ключом, выведенным из этого секрета и отпечатка (`model_crypto.export_encrypted_bundle`). Открытая модель в репозитории не изменяется.
4. Записывает всё в `<папка поставки>/<customer-slug>_<fp8>/`:

| Файл | Назначение |
|---|---|
| `license.dat` | подписанная лицензия, привязанная к отпечатку, с `model_key_secret` — **конфиденциально** |
| `brain_triage_finetuned_<identity12>_<fp8>.zip` | зашифрованная модель: `MANIFEST.json`, `config.json`, `preprocessor_config.json`, `model.safetensors.enc`, `model.safetensors.enc.meta.json`, `study_level_eval.json`, `training_metrics.json` |
| `README_admin_ru.txt`, `README_admin_en.txt` | шаги импорта для ИТ клиники с ожидаемым идентификатором |

5. **Самопроверка** до появления папки: лицензия проверяется собственной проверкой приложения для этого отпечатка, zip распаковывается так же, как его распаковывает `/models/import`, сверяются обе записи `MANIFEST.json`, и веса пробно расшифровываются ключом, выведенным из подписанной лицензии. Ошибка на этом шаге печатает `FAILED [verify_failed]`, завершается кодом 2 и ничего не оставляет (пара ключей, не совпадающая с открытым ключом приложения, — это отказ `private_key`, код 1).
6. Добавляет одну строку в `data/licenses/ledger.csv` (§ 8). Итоговая сводка показывает отпечаток ключа (никогда — сам ключ или секрет).

Прежде чем что-либо копировать, убедитесь, что `<identity12>` в имени zip — идентификатор текущего выпуска (12 символов, которые печатает `scripts/bump_model_release.py --check` и которые указаны в `docs/README.md`), а `<fp8>` совпадает с первыми 8 символами присланного клиникой отпечатка.

---

## 5. Шаг 3 — доставка

1. Скопируйте всю папку `<customer-slug>_<fp8>/` на USB-носитель (лучше зашифрованный). Укажите SHA-256 zip-файла (столбец `bundle_sha256` реестра или `shasum -a 256 <zip>`) в сопроводительной записке; клиника может сравнить его с `certutil -hashfile <zip> SHA256`.
2. Передайте носитель лично или с курьером. **Не** отправляйте `license.dat` по электронной почте или в мессенджере: в нём секрет ключа модели.
3. Если клинический установщик ещё не установлен, передайте его отдельно. Установщик не содержит ни секретов, ни весов собственной модели.

---

## 6. Шаг 4 — импорт на стороне клиники

ИТ клиники выполняет § 5.3–§ 5.4 руководства администратора (кратко — в README-файлах поставки):

1. *Настройки → Лицензия → Импортировать license.dat* → перезапуск приложения → *Настройки → Лицензия* показывает *Лицензировано*, название клиники и срок действия.
2. Скопировать zip на ПК (не распаковывать). *Настройки → Модели ИИ → Импорт пакета модели* → выбрать zip. Приложение копирует его в `<папка данных>\model_inbox\` и вызывает `POST /models/import`.
3. Сервер сверяет записи `MANIFEST.json` для открытого текста и шифртекста, пробно расшифровывает ключом этого ПК, сохраняет предыдущую модель как `brain_triage_finetuned_prev_<старый идентификатор>`, устанавливает новую, перезагружает её без перезапуска и пишет запись аудита. При любой ошибке выполняется откат и возвращается код причины; `bundle_not_for_this_machine` означает, что ключ не совпал (§ 12).

Порядок важен: ключ выводится из лицензии, поэтому пакет нельзя импортировать до того, как парная лицензия станет действующей.

---

## 7. Шаг 5 — проверка идентификатора

Установка завершена, только когда совпадают все четыре пункта:

1. Уведомление после импорта показывает идентификатор — он равен `<identity12>` в имени zip.
2. `http://127.0.0.1:8000/health` на ПК клиники: `"status": "ok"`, `models.brain_triage.loaded: true`, `license.mode: "licensed"`, `version: "1.1.0"`.
3. *Настройки → Модели ИИ* показывает *Триаж исследования — норма / патология (локальный)* с тем же 12-символьным отпечатком и статусом *Валидировано*.
4. Тестовое исследование, проанализированное и экспортированное в PDF, несёт тот же идентификатор модели внизу страницы.

Для удалённой поддержки попросите клинику выполнить *Настройки → О программе → Экспорт диагностики*: `models.json` в архиве содержит карточку идентичности каждой модели, а `license.json` — статус лицензии (но не сам файл). Запишите идентификатор, дату и имя проверившего в примечаниях реестра (§ 8).

## 8. Реестр выдач

`data/licenses/ledger.csv` (игнорируется git; храните резервную копию вместе с ключом поставщика, офлайн) содержит одну строку на каждый запуск выдачи:

| Столбец | Пример | Значение |
|---|---|---|
| `customer` | ООО «Название клиники» | название клиента, как оно записано в лицензии |
| `fp8` / `identity` | первые 8 символов отпечатка / 12-символьный идентификатор модели | какой ПК, какой выпуск модели |
| `issued` / `expires` / `tier` / `features` | 2026-11-09 / 2027-12-31 / pro / … | даты, уровень и список функций лицензии |
| `key_fingerprint` | 12 шестнадцатеричных символов | отпечаток выведенного ключа модели — `python -m src.utils.model_crypto keyinfo` печатает то же значение на ПК клиники (установка из исходников), так что стороны могут убедиться в совпадении, не раскрывая ключ |
| `bundle_sha256` | 64 шестнадцатеричных символа | SHA-256 переданного zip-файла — для сопроводительной записки и проверки копии в клинике |

Реестр никогда не содержит `model_key_secret`, ключ или полную лицензию. Он отвечает на три вопроса: у каких клиник какой выпуск модели, какие лицензии истекают в ближайшие 60 дней и для каких ПК нужно заново выдать новый выпуск. Просматривайте его ежемесячно.

---

## 9. Продление

- В клиническом варианте ключ модели берётся из лицензии: **когда лицензия истекает, вместе с ней перестаёт работать валидированная модель** (`/health` переходит в `degraded`). Начинайте продление за **60 дней** до `expires` и доставляйте не позднее чем за 30 дней.
- Продление — обычный запуск выдачи (§ 4) с тем же отпечатком и новой датой окончания: создаются новая лицензия с новым `model_key_secret` и новый пакет, зашифрованный под неё. Используйте новую папку `--out` вне репозитория (например, по дате: `~/sentinel_deliveries/2027-11-15/`): утилита отказывает с `output_exists`, а не перезаписывает прежнюю поставку. Доставляйте **оба** файла; клиника импортирует лицензию, перезапускает приложение, затем импортирует пакет (§ 6).
- Никогда не отправляйте клинической установке одну только лицензию: новый секрет сделает установленный пакет нечитаемым, пока не будет импортирован парный пакет.
- После каждого обновления приложения клиника заново импортирует тот же пакет (руководство администратора, § 8.1); новая выдача для этого не нужна.

## 10. Если изменилось оборудование ПК

Новая сетевая карта или материнская плата, переименованный хост, переустановленная ОС или клонированная ВМ меняют отпечаток. Тогда:

1. Лицензия становится недействительной (демо-режим), а модель нельзя расшифровать (`/health` → `degraded`). Подписанные заключения и журнал аудита клиники не затрагиваются.
2. Клиника присылает **новый** отпечаток (§ 3).
3. Выполните выдачу заново с новым отпечатком (§ 4) и доставку (§ 5); клиника импортирует лицензию и пакет (§ 6) и проверяет установку (§ 7).
4. Отметьте старую строку реестра как заменённую (примечание: новый `fp8`, дата, причина). Старый пакет на новом оборудовании бесполезен; попросите клинику удалить его из `model_inbox\`.

Если клиника полностью заменяет ПК, сначала перенесите папку данных (руководство администратора, § 6.1), затем выполните те же шаги для нового ПК.

## 11. Развёртывание нового выпуска модели

После того как `scripts/release_pipeline.py` продвинет новую валидированную модель (см. регламент выпуска), каждой клинике нужен новый пакет для её ПК:

1. Отберите в реестре действующие строки (срок не истёк).
2. Повторите § 4 для каждого отпечатка с новой моделью (даты лицензии — по договорённости; каждый раз выпускается новая лицензия).
3. Доставьте и проверьте, как в § 5–§ 7; запишите новый идентификатор каждой клиники в реестр.

Клиники продолжают работать на предыдущем выпуске, пока не импортируют новый пакет; в заключениях всегда печатается идентификатор модели, которая их сформировала.

## 12. Неисправности

| Симптом | Причина | Решение |
|---|---|---|
| `provision_clinic.py` отказывает с `release_check` / `forced_promotion` | модель из `--model` не прошла выпускной барьер или продвинута принудительно | выдавайте только выпуск, прошедший барьер (`scripts/release_pipeline.py`); никогда не поставляйте принудительно продвинутую модель |
| `provision_clinic.py` отказывает с `bad_fingerprint`, `bad_expiry`, `private_key`, `output_exists` или `output_in_repo` | опечатка в отпечатке, дата окончания не в будущем, неверный / нечитаемый ключ поставщика, папка от прежнего запуска, `--out` внутри репозитория | попросите у клиники отпечаток текстом; исправьте дату; используйте `vendor_keys/vendor_private_key.pem`; выберите новую папку `--out` вне репозитория (например, `~/sentinel_deliveries/<дата>/`) |
| Импорт в клинике завершается `license_model_key_missing` | лицензия поставки не импортирована или приложение не перезапущено после импорта | импортируйте `license.dat` из той же папки, перезапустите, импортируйте пакет снова |
| Импорт в клинике завершается `bundle_not_for_this_machine` | лицензия и пакет из разных запусков, неверный отпечаток, или лицензия не импортирована / приложение не перезапущено | сравните `fp8` с *Настройки → Лицензия*; импортируйте лицензию из той же папки и перезапустите; иначе выполните выдачу заново с отпечатком, показанным на экране |
| Импорт не проходит проверку хешей / манифеста | zip повреждён при переносе | сравните SHA-256 с сопроводительной запиской; скопируйте заново |
| `/health` `degraded` через несколько недель после успешной установки | истекла лицензия или изменился отпечаток | § 9 или § 10 |
| Идентификатор в уведомлении отличается от имени zip | импортирован не тот файл | импортируйте zip из папки поставки; проверьте `model_inbox\` на посторонние файлы |

## 13. Правила безопасности

- `vendor_keys/vendor_private_key.pem` подписывает каждую лицензию: храните его только на Mac поставщика и в офлайн-копии. Кто владеет ключом, тот может выпускать лицензии.
- Папка поставки **конфиденциальна**: `license.dat` содержит секрет ключа модели И отпечаток, поэтому `license.dat` вместе с zip-пакетом расшифровывает веса на ЛЮБОМ компьютере (приложение лишь отказывается *использовать* их на другом ПК). Обращайтесь с этой парой как с открытой моделью: передавайте на зашифрованном USB-носителе, никогда не отправляйте оба файла по почте и не храните оба в общей папке. Храните её только до проверки установки клиникой (§ 7), затем удалите локальную копию; постоянная запись — строка реестра.
- Никогда не кладите открытые веса на USB-носитель, в почту или в публичный репозиторий; от поставщика уходят только клинический установщик и папка поставки для конкретного ПК.
- Никогда не коммитьте `data/licenses/`, `*.enc`, `model_inbox/` и папки поставок (они игнорируются git).
- Репозиторий кода публичный: артефакты CI удаляются через 1 день, а сборки по тегу создают только черновики релизов — всё равно скачивайте установщики сразу после сборки и храните их вместе с документами выпуска.
